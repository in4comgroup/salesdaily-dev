> ## ⛔ CRITICAL — Git & version control (overrides every other instruction)
>
> - **NEVER run `git push`. Ever. Under any circumstances.** The user pushes and deploys themselves.
> - **NEVER run `git commit` or `git add`** unless the user explicitly requests that exact action in their current message. A "yes" from an earlier turn does **not** carry forward — approval is per-action and does not persist.
> - **Only make code modifications that have been explicitly discussed and approved** in the conversation. Do not bundle in unrelated edits.
> - When work is ready, **stop and report** — let the user stage, commit, and push. If you believe a commit/push is warranted, *ask*; do not act.

## Commands

- `pnpm dev` — start Next.js dev server. Runs with `NODE_OPTIONS=--max-old-space-size=8192 --dns-result-order=ipv4first` (same for `pnpm build`). The heap flag dates from the Vercel Workflow SDK era (`withWorkflow()` bundled the whole app on boot and idled at ~4 GB); the SDK is gone, but the app graph is still large, so keep it — a dev server that hits Node's default heap ceiling **dies with no error message** (the log just stops). If it recurs, `rm -rf .next` first and prefer `next/dynamic` for heavy pages (see the lazy `TabAssistant` in `/analytics`).
- `pnpm build` — production build (`output: "standalone"` — what the Docker image ships). Needs ~8 GB RAM; type-checking is skipped (`typescript.ignoreBuildErrors`).
- `docker build --build-arg NEXT_PUBLIC_APP_URL=https://dev.salesdaily.ru -t crm:test .` — local image build (see **Deployment** below).
- `pnpm lint` — ESLint
- `pnpm db:migrate` — apply the versioned SQL sequence through `scripts/migrations/run.cjs`; only use against an explicitly authorized database.
- `pnpm db:migrations:status` — verify migration history/checksums and report applied/available counts; requires an authorized database connection.
- `npx drizzle-kit generate` — optional SQL **drafts only** in `tmp/drizzle-drafts`; review and extract the intended change into the canonical SQL sequence below.
- **Do not run `drizzle-kit push` or `drizzle-kit migrate` against project environments.** They bypass the canonical runner/history; push can remove Search V2 objects absent from `schema.ts`.

## Database migrations — rules for code generation

Before changing database-backed code or `src/db/schema.ts`, read
[docs/deploy/database-migrations.md](docs/deploy/database-migrations.md), inspect
`db/migrations/manifest.json` and the relevant existing SQL.

- **Every schema change needs reviewed SQL in the same change as the code.** Updating `schema.ts` alone does not migrate PostgreSQL. For ORM-managed objects, keep SQL and `schema.ts` consistent; SQL also owns functions, generated columns and indexes intentionally absent from the ORM model.
- **One migration history:** `db/migrations/manifest.json` is the ordered executable sequence; `crm_migrations.history` is its database journal. Add the next consecutively numbered `db/migrations/NNNN_description.sql` and append its path to the manifest. Do not introduce a second runner, Drizzle journal, startup migration, initContainer or per-replica migration.
- **Applied SQL is immutable.** Do not edit/rename/remove historical files, rewrite journal checksums, reorder entries, or regenerate the registration fixture to hide drift. Make corrections with a new migration. Preserve `db/baseline/0000_baseline.sql` and `0001_deal_funnel_stage_settings.sql` byte-for-byte. `crm-current-schema.sql` is a diagnostic snapshot, never an executable migration.
- **Preserve PostgreSQL objects outside `schema.ts`**, especially Search V2 functions, product generated columns and GIN/trigram indexes. Never treat their absence from the ORM model as permission to drop them. Generated Drizzle output is only a draft and may contain an unwanted full schema creation.
- **Design for rolling deployment:** migration Job runs before rollout while old replicas still serve requests. Prefer additive expand/contract changes; stage renames, type changes, NOT NULL and removals across compatible releases. Explain lock/rewrite impact and compatibility with the previous application version. No destructive operations or automatic database rollback by default.
- **New SQL runs inside a runner-owned transaction:** no BEGIN/COMMIT/ROLLBACK or commands requiring execution outside a transaction (e.g. CREATE INDEX CONCURRENTLY). Separate enum addition from use of its new value. Keep long backfills out of deployment migrations; plan bounded, resumable batches separately.
- **Verify on disposable PostgreSQL 17**, both from empty and from the previous schema with representative test data. Run `MIGRATION_TEST_DATABASE_URL="$TEST_DATABASE_URL" node scripts/migrations/test.cjs` and `bash scripts/migrations/test-deploy.sh`; add change-specific checks for resulting schema/data and preservation of relevant manual objects. Report actual checks separately from checks awaiting CI/cluster access. Never infer PG17 acceptance from PG16-only tests.
- **Existing environments require explicit operator registration** of 0000+0001 using `register-existing`, with its schema validation intact. Do not automatically register, replay baseline on a nonempty database, or skip checks based on one table. Registration, applying SQL to existing environments and changing the cluster require separate authorization.
- **Deployment uses `.github/workflows/dev.yml`:** one managed Kubernetes Job uses the same image digest/SQL/runner as the application, reads DATABASE_URL from the existing cluster Secret, and must succeed before Deployment changes. Preserve the failure/timeout gate. A shorter/changed migration history in an old image must fail; application rollback requires compatible code packaged with current migration history, never an automatic database rollback.
- Do not read/print real secrets or env files, copy DATABASE_URL into GitHub, or log connection strings/SQL data. `pg` accepts `sslmode=no-verify`; libpq clients (`psql`/`pg_dump`) require a separately prepared compatible SSL configuration. Use variable names/examples in commands and documentation.

### ⛔ STRICT: `drizzle-kit generate` output → canonical migration (mandatory checklist)

`drizzle-kit generate` output is **never** a migration as-is. It is raw input. Every item below is a hard gate: check it, and fix it or stop. When you hand a migration to the user, report each gate as pass / fixed / blocked. Do not skip a gate silently.

**A. Get a clean delta (not a full-schema dump)**
1. `drizzle.config.ts` writes to `tmp/drizzle-drafts` (often absent). With no `meta/_journal.json` + snapshot there, generate emits `CREATE` for the **whole** ORM schema. Never copy that.
2. To get only the delta: on the **unchanged** `schema.ts` (e.g. `git stash` the schema edit), run `npx drizzle-kit generate` once to create the snapshot; restore the edit; run it again. Only the **second** file is the candidate delta. Delete the first one.
3. The snapshot comes from `schema.ts`, not from the real DB. `schema.ts` can drift from `db/baseline/0000_baseline.sql` + later migrations. Cross-check every statement against the baseline + `db/migrations/*.sql` (does the object/column already exist? different type/default/name?).
4. Renames: drizzle asks "rename or create+drop?" interactively. Never accept create+drop for an existing column/table (data loss). See D.

**B. File and manifest format (runner rejects anything else)**
5. Rename the file to the next consecutive number after the last manifest entry: `db/migrations/NNNN_description.sql`. Name must match `^NNNN_[a-z0-9_]+\.sql$` (lowercase, digits, `_` only). Drizzle's `0000_random_name.sql` numbering is always wrong here.
6. Append the path **relative to `db/migrations/`** (e.g. `"0002_add_x.sql"`) to the END of `db/migrations/manifest.json`. Never reorder, edit, or remove existing entries/files.
7. Do not commit anything under `tmp/drizzle-drafts`.

**C. Transaction rules (runner owns one transaction per file)**
8. Remove any `BEGIN;` / `COMMIT;` / `ROLLBACK;`. The runner fails the file if it finds them (plpgsql `BEGIN … END` bodies are fine).
9. No `CREATE INDEX CONCURRENTLY`, `VACUUM`, `ALTER SYSTEM`, `CREATE DATABASE`, or anything else that cannot run inside a transaction. Long index builds → separate manual operation with its own approval.
10. `ALTER TYPE … ADD VALUE`: allowed, but the new value must NOT be used (default, insert, update, check) in the same file. Use it in a later migration.
11. Runner limits: `statement_timeout = 120s`, `lock_timeout = 5s`. Any statement that may exceed them (big table rewrite, large UPDATE/backfill) does not belong in a deploy migration.
12. `--> statement-breakpoint` lines are SQL comments. They can stay or go.
12a. **Schema-qualify every object name** (`"public"."client"`, `"public"."user"`, types, functions). `0000_baseline.sql` runs `set_config('search_path', '', false)` for the whole runner session, so on a fresh database every later file sees an EMPTY search_path and an unqualified `"client"` fails with 42P01. Drizzle emits unqualified table names (`ALTER TABLE "client"`, `CREATE INDEX … ON "client"`) — always rewrite them. (Found by the 0002 PG17 test; it passes on an existing DB, so only the empty-DB test catches it.)

**D. Rolling-deploy safety (old pods still run against the new schema)**
13. `ADD COLUMN … NOT NULL` without a DEFAULT on an existing table → fails on non-empty tables and breaks old code. Add nullable (or with a constant DEFAULT) first; NOT NULL in a later release after backfill.
14. `DROP COLUMN` / `DROP TABLE` / `DROP TYPE` / `DROP INDEX` / `DROP FUNCTION` → remove, unless the user explicitly approved a contract-phase removal and no supported app version still uses it.
15. `RENAME COLUMN` / `RENAME TABLE` → replace with expand/contract (add new, dual-write, switch reads, drop later). One-step rename breaks old pods.
16. `ALTER COLUMN … SET DATA TYPE` → check for a table rewrite/lock. Heavy change → new column + backfill + switch.
17. Enum value removal/rename: drizzle recreates the type (drop + create). Never accept it.
18. Backfills (`UPDATE` of many rows) → out of the deploy migration; plan batched, resumable, separately.

**E. Objects outside `schema.ts` must survive**
19. Reject any statement that drops or alters Search V2 objects (`immutable_unaccent`, `translit_cyr_lat`, `to_or_tsquery`, their triggers), product generated columns, GIN/trigram indexes, or the `unaccent` / `pg_trgm` extensions. Their absence from `schema.ts` is not a reason to touch them.
20. Never touch the `crm_migrations` schema or its `history` table.

**F. Verify before handing over**
21. ⚠ CI (`.github/workflows/migrations.yml` → `scripts/migrations/test.cjs`) tests ONLY the runner + 0000/0001 on PG17. It does **not** apply new `000N` files. The first real execution of a new file is the deploy Job. So verify locally on a disposable PostgreSQL 17 (never a project DB), e.g.:
    ```sh
    docker run --rm -d --name crm-mig-pg17 -p 55432:5432 -e POSTGRES_PASSWORD=test postgres:17
    DATABASE_URL=postgresql://postgres:test@localhost:55432/postgres node scripts/migrations/run.cjs apply   # empty → all files
    DATABASE_URL=postgresql://postgres:test@localhost:55432/postgres node scripts/migrations/run.cjs apply   # 2nd run = no-op
    DATABASE_URL=postgresql://postgres:test@localhost:55432/postgres node scripts/migrations/run.cjs status
    docker rm -f crm-mig-pg17
    ```
    Also apply it on a DB that holds representative rows in the affected tables (catches NOT NULL / cast / unique failures).
22. If the change also touches `schema.ts`: run generate again after the migration is final. The output must be empty (no remaining diff between `schema.ts` and the snapshot).
23. If Docker / PG17 is not available, say so plainly. Do not claim the migration is verified.

## Architecture

### Route Groups

- `src/app/(auth)/` — public auth pages (sign-in, sign-up, accept-invitation; `/sign-in/otp` is a redirect to `/sign-in`)
- `src/app/(protected)/` — auth-gated pages; session checked server-side in `layout.tsx`, redirects to `/sign-in` if unauthenticated
- `src/app/(protected)/settings/` — platform-admin-only (users & orgs management, templates, sources, **«Сброс источника» = admin source teardown/reset**, **«Использование»** = LLM usage/cost per org / process / model / day, **«Модели»** = Yandex price sync, model prices + markup, daily caps, Topics flag — see `src/lib/CLAUDE.md` § LLM usage metering)
- `src/app/o/[token]/` — **public, no-auth** guest order-confirmation page (capability = the token). Outside `(protected)` so the layout gate doesn't apply; there is no auth middleware. Details in `src/app/CLAUDE.md` § "Guest order-confirmation links".

### API Routes (overview)

Subsystem-specific details live in `src/app/CLAUDE.md`. Key routes:

- `api/auth/[...all]` — better-auth catch-all handler
- `api/admin/*` — admin-only (user-organizations, organizations CRUD)
- `api/chat` — AI chat streaming (60s max duration)
- `api/emails`, `api/chats`, `api/drive` — Nylas email + Google Chat + Google Drive integrations (listing + attachment download proxies)
- `api/products` — org-scoped catalog listing. GET only (read-only for now): `?q=&limit=&offset=` + attribute filters → `{ rows, total }` for the server-paginated Products table; `?categories=1` / `?filterOptions=1` for the filter dropdowns. Single-value attribute filters plus three **multi-select** export-relevant ones — `colors` / `regions` / `countryNames` — sent as **repeated params** (comma-safe; some region values contain commas) and gated as `IN (…)`. Search probes `name` + named `additional_metadata` text fields **by value** (not the JSON blob). Management mutations (create/edit/stock) are a deliberate later step. Details in `src/app/CLAUDE.md` § "Products".
- `api/products/export` — GET → XLSX **price list** (one sheet per country, hierarchical region → color → vendor → name). `?countries=&regions=&colors=` (repeated params) narrow it; every OTHER active filter is ignored by the export. No params → whole active catalog. Built via `buildPriceListWorkbook` (ExcelJS). Details in `src/app/CLAUDE.md` § "Products → Price-list export".
- `api/orders` — org-scoped sales orders. `GET ?q=&status=&limit=&offset=` → `{ rows, total }`; `?id=…` → single order detail (header + line items + link meta); `?clientOptions=1` → client picker. `POST` creates a **draft** (client + line items from the catalog); `PUT` is a draft-only content update (status transitions are NOT here). Details in `src/app/CLAUDE.md` § "Orders".
- `api/orders/[id]/link` — order status transitions that drive the guest-link lifecycle (the **only** mint/revoke path). `POST { action: send|resend|reopen|pullback|cancel|finalize, recipientEmail? }`. `send`/`resend`/`reopen` require a valid recipient email (defaults to the client's) and return the raw guest URL once; `finalize` (confirmed→finalized) is internal-only. Details in `src/app/CLAUDE.md` § "Guest order-confirmation links".
- `api/order-requests` — LLM-assisted "order from request" assembly. `POST { clientId, rawText, comment? }` creates an `order_request` and runs ONE LLM split of the pasted free-text client message into intent items (`maxDuration = 120`); `GET ?id=` → `{ request }` (header + items); `PUT { id, action }` switches on `linkOrder | itemStatus | status` for wizard progress. The wizard then drives the existing manual order builder. **No Vercel Workflow** — durable rows + a UI wizard over the draft order. Details in `src/app/CLAUDE.md` § "Order from request (LLM-assisted assembly)".
- `api/analytics` — org-scoped **sales analytics** for the «Аналитика» page. `GET ?bounds=1` → the org's first/last order date; `GET ?from=&to=` → one payload covering every tab (KPI totals + equal-length previous window, day/month/year series, per-seller / per-department / per-client-type / per-status slices, order-size histogram, product slices by country/region/color/type/sugar, top products/clients, client scatter). Read-only. Revenue counts only `finalized` + `confirmed` orders and is net of the per-client discount. Details in `src/app/CLAUDE.md` § "Analytics".
- `api/analytics/assistant` — streaming chat for the «ИИ ассистент» tab. ONE tool (`queryAnalytics`) over the analytics **semantic layer** (`src/lib/analytics-semantic.ts` = the tunable measure/dimension/chip vocabulary; `src/server/analytics-semantic.ts` = the whitelist→SQL engine over the same CTE the page uses, so chat numbers can't contradict dashboard numbers). The model never writes SQL and the org id is bound from the session, never from model input. Details in `src/app/CLAUDE.md` § "«ИИ ассистент» tab".
- `api/search` — org-scoped **global search** across companies/contacts/deals/orders, reachable from every page's header (`<GlobalSearch/>`). `GET ?q=` → capped, RANKED hits per entity type, matched through the **Search V2 normalisation** (Cyrillic→Latin translit + unaccent + a pg_trgm fuzzy arm), so «АСТ» finds «AST» and «НТехЛаб» finds «NTechLab». Read-only. Details in `src/app/CLAUDE.md` § "Global search".
- `api/clients`, `api/contacts`, `api/tasks`, `api/deals` — org-scoped CRUD. `api/clients` GET additionally takes `?tab=<customers|potential|supplier|partner|unclassified>&status=&limit=&offset=` for the Companies page's scroll-loaded feed (`listClientsFeed`) — omitted entirely, it keeps the old whole-org `listClients()` shape. `api/contacts` GET similarly branches to a paginated/alphabetical `listContactsPaged()` when any of `q/status/clientId/limit/offset` are present (the standalone `/contacts` page), otherwise the old unparameterized shape. `api/tasks` PUT supports `statusOnly: true` for the card's quick-status dropdown; `api/deals` PUT supports `statusOnly: true` + `status` for the quick cancel/delete/restore shortcut (deal lifecycle is an `active | cancelled | deleted` enum — see `src/app/CLAUDE.md` § "Deals") and `moveOnly: true` + `funnelStageId` + `position` for the **kanban drag** (persists manual order via `deal.position`, a fractional-indexing key; the `/deals` page is a dnd-kit kanban board — see `src/app/CLAUDE.md` § "UI: Deals kanban board"), accepts a multi-contact `contactIds[]` payload, and exposes `?clientOptions=1` / `?contactOptions=1&clientId=…` / `?funnelStages=1` for the create form. It also serves the board's «Настройки стадий» dialog: `GET ?stageSettings=1` / `PUT { stageSettings: [{ id, displayName, isHidden }] }` (stage `display_name` + `is_hidden`; the first save copies the system funnel into the org and adds the pre-pipeline «Контакт до запроса» stage) — see `src/app/CLAUDE.md` § "Pre-pipeline stage + «Настройки стадий»".
- `api/discovery/{preview,apply}` — unified "Discover from sources" flow (replaces the three legacy `api/clients/discover` + `api/contacts/discover` + `api/contacts/link-to-clients` routes). `preview` POST runs one read-only scan and returns company / contact / link candidates; `apply` POST creates the selected clients + contacts, links them (same-run linking via inferred `webUrl`), and stamps `source_item.discovery_scanned_at`. Both re-export their types for client components. Details in `src/app/CLAUDE.md` § "Unified discovery from sources".
- `api/clients/enrich/{pending,review}` + `api/clients/[id]/enrich{,/resolve}` — **batch client web-enrichment** (fills missing website/email/phone/address from web search, built on the existing `lookupClientOnWeb`). `pending` GET → worklist `{ ids, total }`; `[id]/enrich` POST (`maxDuration=60`) processes ONE client → auto-applies a single high-confidence match else parks it for review; `review` GET + `[id]/enrich/resolve` POST drive the manual disambiguation queue. Browser-driven one-by-one loop (the only mode) keyed off `client.enrichment_status IS NULL`. Details in `src/app/CLAUDE.md` § "Batch web enrichment".
- `api/org-identity{,/[id]}` — owner-managed **own-organisation identity registry** (org-scoped dictionary of extra names/synonyms, websites and postal addresses that identify the CRM owner's OWN company, so parsing/discovery never turn it into a client). `GET` → `{ entries, canManage }`; `POST` (owner) adds + returns the already-created clients/contacts that match it (report-only — the owner deletes them row by row); `DELETE /[id]`. Read by `loadOwnOrgIdentity` + `getOrgIdentity`. Details in `src/app/CLAUDE.md` § "Own-organisation identity registry".
- `api/blocklist{,/[id],/from-entity}` — owner-managed **discovery blocklist** (org-scoped dictionary of business-irrelevant companies/people/domains/emails). `GET` → `{ entries, canManage }`; `POST` (owner) adds + retroactively sweeps matching rows to `status='blocked'`; `DELETE /[id]`; `POST /from-entity` blacklists an existing client/contact. Honored by discovery (candidates never surface) + parse-time attribution. Details in `src/app/CLAUDE.md` § "Discovery blocklist".
- `api/admin/teardown/{sources,preview,execute}` — **admin source teardown/reset**: hard-deletes everything one source produced (items + R2 + cards + the clients/contacts/deals/tasks it triggered, via re-aggregated discovery collision keys) and resets the sync cursor, so a demo/test re-runs "as if new". `preview` POST → blast radius; `execute` POST (`maxDuration=300`) typed-confirm + hard delete, audited in `teardown_log`. Details in `src/app/CLAUDE.md` § "Source teardown / reset".
- `api/cards` — Truffalo Cards CRUD (LLM-generated dashboard signals). `GET` lists; `GET ?id=` returns one card (used by the `new_order` card's "Create order" handoff to /products). PUT accepts `action: "accept" | "reject"` shortcuts (rejection requires `rejectionReason`); otherwise applies a partial update. The `new_order` category drives a "Create order" button → opens the New Order dialog on /products prefilled with the client + verbatim source message. Details in `src/app/CLAUDE.md`.
- `api/cards/generate` — LLM-driven card generation from sources (the Truffalo Cards pipeline). POST runs the chosen Custom rule against eligible source items, inserts cards with linked clients/users. GET returns a preview count for the explore dialog. `maxDuration = 300`. Details in `src/app/CLAUDE.md`.
- `api/deals/discover` — LLM-driven deal discovery from sources. POST runs the chosen Custom rule against eligible source items, creates new deals, or moves existing open deals to a different funnel stage (mirrors `/api/cards/generate`). GET returns a preview count for the dialog. `maxDuration = 300`. Details in `src/app/CLAUDE.md`.
- `api/invitations/[id]` and `api/invitations/check` — **public** (no-auth) endpoints used by the accept-invitation page and sign-up pending-invite guard. Details in `src/app/CLAUDE.md`.
- `api/sources/{items,sync,r2/save,dropoff/upload,whatsapp/upload,telegram/fetch,org,stored,r2/pending-ids,items/pending-parse-ids}` — Sources subsystem. All org-scoped via `session.session.activeOrganizationId`. Per-row mutations verify tenant scope via `assertSourceItemInScope` / `assertSourceInScope` (typed errors → 403/404). `whatsapp/upload` is the only multipart route here — supports chunked client-side uploads via the `<WhatsAppArchiveDialog>`. `telegram/fetch` POST runs a manual `getUpdates` pull for a per-org Telegram source (the "Fetch" button — mainly local dev; 409s when a webhook is active). `pending-ids` and `pending-parse-ids` power the batch upload / parse controls. Details in `src/app/CLAUDE.md`.
- `api/webhooks/telegram/[sourceId]` — **public, no-auth** Telegram webhook (outside `(protected)`; the path `sourceId` + the per-source secret echoed in the `X-Telegram-Bot-Api-Secret-Token` header are the capability — org-unscoped, like the guest order link). `POST` delegates to `ingestTelegramUpdate` → resolves source→org by path id, verifies the secret, persists DM text as a `chat_message` source_item, acks the chat. Node runtime, fast-ack. Details in `src/app/CLAUDE.md` § "Telegram Bot (Sources)".

### Auth Flow

- Server sessions: `src/lib/get-session.ts` uses `cache()` to dedupe session calls per request.
- Client auth: `src/lib/auth-client.ts` exports `authClient` with organization, admin, apiKey, emailOTP plugins. (Polar billing was removed — RU-market billing is a separate later step.)
- Auth config: `src/lib/auth.ts` — 7-day sessions with **`session.cookieCache` enabled (5-min signed cookie)** so navigation doesn't hit the DB every request — without it a transient Neon blip made `getSession()` return null → the `(protected)` layout bounced to `/sign-in`, reading as a random mid-session logout. `databaseHooks.user.create.after` skips default-org creation when the new user's email has a live (pending + non-expired) invitation — otherwise they'd end up in two orgs (default + inviter's).
- Sign-in methods: **email OTP only** (6-digit, 5 min expiry, 3 attempts). Password, password reset, admin «set password», Google and GitHub OAuth were removed; existing users sign in with a code sent to the same email. Every screen is two steps (email → shadcn `InputOTP`, shared `src/components/forms/otp-code-step.tsx`, helpers in `src/lib/auth-otp-client.ts`) and uses OTP type `sign-in`. `disableSignUp: false`: the first code sign-in of a new email creates the user (name from the form; fallback = email part before `@`, `withFallbackName`). **Sign-in vs sign-up gate** (`src/lib/auth-otp-gate.ts`, `hooks.before`): a code request without header `x-auth-intent: sign-up` for an UNKNOWN email is rewritten to type `email-verification`, so better-auth answers `{ success: true }` and sends nothing — `/sign-in` never creates accounts and never shows whether an account exists. `/sign-up` and the invitation page send the header. Do not return a response from that hook: better-auth copies the request headers (Content-Length) onto it → `ERR_CONTENT_LENGTH_MISMATCH` in browsers. OTP emails go through `sendEmails` in `src/lib/email.ts`.

### Role Model (Two-Tier)

- **Platform roles** (`user.role`, via admin plugin): `user` | `admin`. Controls access to Settings page + platform-wide admin functions.
- **Organization roles** (`member.role`, via organization plugin): `owner` | `admin` | `member`. Controls within-org permissions (member management, org editing, invitations).
- Independent: a platform `user` can be org `owner`.

### Multi-Tenancy

Session stores active organization (id, name, slug). **The org `logo` is intentionally NOT on the session** — logos are base64 data URLs (often 100KB+) and `auth.ts`'s `cookieCache` serialises every session field into the signed session cookie, so a logo overflowed the ~16KB HTTP header limit → `431 Request Header Fields Too Large` on every authenticated request (dev + Vercel). The sidebar loads the logo server-side in `(protected)/layout.tsx` and passes it as the `orgLogo` prop instead (`user.image` data URLs are the same hazard — keep avatars/logos as hosted URLs, not data URLs). All feature tables (clients, contacts, tasks, **deals**, **products**, **orders**, **order_requests**, rules, **sources, source_items**, **discovery_blocklist**) are org-scoped via `session.session.activeOrganizationId`; no cross-org read/write. Permission checks in `src/server/permissions.ts`. **Exception:** the admin source-teardown tool (`/api/admin/teardown/*`) is platform-admin-only and intentionally cross-org (it resolves one source's owning org and operates within it). **Exception:** the guest order-confirmation flow (`/o/[token]` + `order_access_link`) is intentionally org-unscoped — the opaque token *is* the authorization, and the resolver loads the order strictly by `grant.order_id`.

**Deal funnel stages scope model** (`deal_funnel_stage`):
- Same `is_system = true` / `owner_organization_id = <orgId>` split as `source`. Seeded as 7 system rows (Qualification 0.05 → Closed 1.0 / Rejected 0.0) via `scripts/seed-deal-funnel-stages.ts`.
- `listDealFunnelStages()` resolves with **org-or-system fallback** (not union): if any active org-scoped stage rows exist, only those are returned; otherwise the system bucket. Lets each org customise its funnel later without a migration of existing deals.
- See `src/app/CLAUDE.md` § "Deals" for the full picture.

**Sources scope model** (`source` + `source_item`):
- Every source row carries either `is_system = true` (platform-wide singleton, currently unused) or `owner_organization_id = <orgId>` (per-org). After the org-scoping refactor, all five seeded sources (Emails / Google Chat / Google Meet / Google Drive / Files Drop Off) are per-org.
- `source_item.organization_id` is denormalised from `source.owner_organization_id` at upsert / parse-time so org-filtered queries don't have to join `source`.
- API routes for sources (`/api/sources/*`) gate on `session.session.activeOrganizationId` and verify per-row tenant scope via `assertSourceInScope` / `assertSourceItemInScope` in `src/server/{sources,source-items}.ts`. AI chat tools (`/api/chat`'s `searchSourceItems` / `getSourceItemContent` / `showSourceItemsInPanel`) take the active org id from the session and pass it through `listSourceItems({ organizationId })` + `getSourceItemMarkdown(id, { requireOrganizationId })`.
- See `src/app/CLAUDE.md` § "Sources scope, tabs & permissions" for the full picture.

### Daily Orchestration (sync → parse → upload pipeline)

Scheduled batch processing of the Sources subsystem. The business logic is engine-agnostic; the scheduler is a **Kubernetes CronJob** that calls one HTTP route. (It used to be Vercel Cron + the Vercel Workflow SDK; both were removed in the move to Kubernetes — that split is what made the swap a two-file change.)

- **`src/server/orchestration/`** — engine-agnostic. `runDailyPipeline({ trigger })` is the single callable entry point: runs `runFullSync()`, then loops `parseSourceItem()` over `listPendingParseIds()`, then loops `uploadSourceItem()` over `listPendingUploadIds()`. Sequential by design (MVP scale; PHASE2 #2). Per-item failures are isolated three layers deep — `parseSourceItem`/`uploadSourceItem` already return-on-error, the loops wrap each call in their own try/catch, and `pipeline_run.errors_json` records every failure without crashing the run. Caps + cron schedule live in `src/server/orchestration/config.ts` (PHASE2 #12 tracks lifting these to system_settings).
- **Per-source automation gate (`source.automated_parsing_is_allowed`)** — boolean column, default `true`. All three orchestration phases filter on it: `runFullSync()` skips sources with the flag off; `listPendingParseIds()` / `listPendingUploadIds()` (and their `count*Total` siblings) inner-join `source` and require the flag to be true, so any items already in the queue under a flagged-off source are also skipped. Manual UI actions (`/api/sources/{sync,items/[id]/parse,items/[id]/reparse,r2/save,dropoff/upload}`) bypass the flag — operator intent overrides the schedule. Org owners flip it from the Sources page "Manage organization sources" tab; platform admins flip it from `/settings`.
- **`src/server/r2/upload-source-item.ts`** — `uploadSourceItem(itemId)` server function extracted from the manual R2 save route. Returns `{ ok, … }` instead of throwing. The manual `/api/sources/r2/save` route is now a thin auth wrapper that calls it; the orchestration layer calls the same function directly.
- **`pipeline_run` table** (`src/db/schema.ts`) — one row per orchestration run with per-phase counts (`syncSourcesSucceeded` / `parseComplete` / `uploadFailed` / etc.) and a bounded `errorsJson: { phase, sourceId?, sourceItemId?, message }[]`. Future Sources-page widget reads from here.
- **`src/app/api/cron/daily/route.ts`** — the scheduler entrypoint. Validates `Authorization: Bearer $CRON_SECRET` in production (skipped in dev), then runs `runDailyPipeline({ trigger: 'cron' })` **synchronously inside the request** and returns 200/500 by outcome, so the caller's exit status mirrors the run. `maxDuration = 3600`.
- **`deploy/k8s/app/cronjob.yaml`** — the schedule (`0 3 * * *`, `timeZone: Etc/UTC`). A `curl` pod calls `http://crm/api/cron/daily` over the in-cluster Service (no ingress → no proxy timeout) with `--fail-with-body`. `concurrencyPolicy: Forbid` prevents overlapping runs; `backoffLimit: 0` because a retry would start a second `pipeline_run`. **Duplicates `ORCHESTRATION_CONFIG.cron`** — keep both in sync. ⚠ Currently **`suspend: true`**: while Vercel+Neon is still production, the cluster runs on a COPY of the DB with the same item ids, so a run would re-sync the same mailboxes and overwrite the same R2 keys. Flip on cutover day (and turn the Vercel cron off). Manual run: `kubectl -n salesdaily create job --from=cronjob/crm-daily-pipeline manual-$(date +%s)`.
- **`src/app/api/admin/pipeline/run/route.ts`** — admin-gated POST that invokes `runDailyPipeline({ trigger: 'manual' })` synchronously (`maxDuration = 300`). Lets you exercise the full chain without waiting for cron.
- A run that dies mid-way (pod restart during rollout) leaves its `pipeline_run` row at `status='running'`; if that becomes a problem, add a stale-run sweep keyed on `status='running' AND started_at < now() - 1h`.

## Deployment

Runbook: `deploy/k8s/README.md`. What is set up, cluster limitations, what must never be deleted, how TLS works: `docs/deploy/k8s-dev-cluster.md`. DB migration log: `docs/deploy/db-migration-neon-to-postgres.md`.

- **Image**: `Dockerfile` (deps → `next build` → standalone runner, non-root uid 1001) built by `.github/workflows/docker-image.yml` in the GitHub Environment **`dev`** (manual dispatch or push to `main`) → `ghcr.io/in4comgroup/salesdaily-dev:dev-sha-<short>`. The `dev-` tag prefix is load-bearing: `NEXT_PUBLIC_*` are baked in, so a dev image must never be deployed to prod. Prod (`salesdaily.ru`) will need its own Environment + tag prefix.
- **Deploy**: `.github/workflows/deploy.yml` — manual button (Actions → deploy → branch + optional `tag`; empty = `dev-sha-<commit>` of that branch, a past tag = rollback). Checks the image exists, overrides the image in `deploy/k8s/app` on the runner (`kustomize edit set image`, never committed), `kubectl apply -k`, `rollout status`, `/api/health`. Authenticates as ServiceAccount `github-deployer` (`deploy/k8s/infra/github-deployer.yaml` — namespace-scoped, no delete, no Secrets) via `KUBE_SERVER` / `KUBE_CA_DATA` / `KUBE_TOKEN` secrets in the GitHub Environment `dev`. **Consequence: `newTag` in `kustomization.yaml` is not what runs** — a laptop `kubectl apply -k` with a stale tag rolls the cluster back. Setup + usage: `docs/deploy/ci-deploy.md`; manual fallback: `docs/deploy/k8s-release.md`.
- **Cluster**: h3llo managed Kubernetes `salesdaily-dev` → **`https://dev.salesdaily.ru`**. `kubectl apply -k deploy/k8s/app` (namespace `salesdaily`; Deployment ×2 with `/api/health` probes — that route is DB-free on purpose, so a DB blip doesn't restart pods; Service; Ingress; CronJob). Secrets `crm-env` + `ghcr-pull` are created by hand, never committed.
- **⛔ Public IP `45.93.22.251` is bound to Service `traefik/traefik`** (provider rule — not reserved for the project). Deleting that Service, `helm uninstall traefik`, or deleting the `traefik` namespace loses the IP and breaks DNS. Change Traefik **only** via `helm upgrade --version 41.7.1 -f deploy/k8s/infra/traefik-values.yaml`.
- **The hosted control plane cannot reach in-cluster Services** (no konnectivity; ClusterIP routing). Consequence: **admission webhooks and aggregated APIs time out** — cert-manager doesn't work (installed but unusable; `infra/cert-manager-values.yaml` + `infra/cluster-issuer.yaml` are parked), and any operator with a webhook will hit the same wall. TLS is therefore **Traefik's built-in ACME** (resolver `letsencrypt`, Ingress annotation `traefik.ingress.kubernetes.io/router.tls.certresolver`), storing `acme.json` on a RWO PVC → Traefik is a single replica with `Recreate`.
- **Until cutover (Vercel + Neon remain production)** the cluster runs on a COPY of the DB with the same ids. Do NOT, from the cluster instance: un-suspend the CronJob, run "Синхронизировать и обработать" on sources (double mailbox reads + overwriting the same R2 keys), or save Telegram bot credentials (re-registers the bot's webhook to `dev.salesdaily.ru`, stealing it from prod).
